# 项目架构待改进点

本文基于当前仓库代码结构整理，目标不是全面重画架构，而是列出当前最值得处理的结构性问题，便于后续拆分重构任务。

## 1. 顶层启动与装配职责过重

### 现状

- `src/cli/commands/root.ts` 承担了过多系统装配职责：模型、权限、MCP、插件、技能、远程模式、会话恢复、Plan 模式、Swarm、Bridge、渲染启动都在这里汇总。
- `src/main.tsx` 也承担了较多初始化与运行前决策逻辑。

### 问题

- 启动链路长，理解成本高。
- 新功能容易继续堆到入口层，形成“总装文件”。
- 不同运行模式之间的共享逻辑与分支逻辑耦合，回归风险高。

### 改进方向

- 把 `root.ts` 拆成明确的装配阶段，例如：
  - runtime bootstrap
  - capability discovery
  - session restore
  - tool/mcp/plugin assembly
  - mode activation
  - REPL launch
- 为不同模式建立独立 assembly 模块，例如 interactive、print、remote、assistant。
- 让 `main.tsx` 只保留启动编排，不直接持有过多业务判断。

### 优先级

高

## 2. REPL 顶层组件过重

### 现状

- `src/screens/REPL.tsx` 同时处理 UI 渲染、输入控制、通知、权限弹窗、远程会话、Swarm、Bridge、Transcript、快捷键、状态拼装等多类职责。

### 问题

- UI 容器与会话控制逻辑耦合严重。
- Hook 很多，依赖面大，新增功能时容易互相影响。
- 单文件过重，不利于局部测试和定向重构。

### 改进方向

- 将 REPL 拆成“会话控制器 + 视图层 + 模态层 + 输入层”。
- 把远程连接、权限流、Transcript、队友视图这类能力抽成 feature container。
- 减少 REPL 直接感知的全局状态数量，改为聚合 selector 或 façade。

### 优先级

高

## 3. QueryEngine 与 query loop 的职责边界仍可继续收敛

### 现状

- `src/QueryEngine.ts` 负责会话级状态。
- `src/query.ts` 负责单轮 query loop、compact、错误恢复、tool 调度、停止钩子、预算控制等。

### 问题

- 当前分层方向是对的，但 `query.ts` 仍然过于中心化。
- 查询生命周期里的策略逻辑很多，功能继续增长时会让单轮执行链变得更难维护。

### 改进方向

- 明确拆分单轮执行阶段，例如：
  - prompt assembly
  - model request
  - stream handling
  - tool execution
  - recovery
  - continuation decision
- 把 compact、预算控制、恢复逻辑改为更独立的 pipeline/stage。
- 为 QueryEngine 与 query loop 之间建立更清晰的数据边界，减少隐式状态共享。

### 优先级

高

## 4. 全局运行时状态与 UI 状态双中心，边界需要继续清晰化

### 现状

- `src/bootstrap/state.ts` 管理全局运行时、遥测、会话元数据、模型用量等。
- `src/state/AppStateStore.ts` 管理 React/Ink 共享状态。

### 问题

- 双状态中心本身合理，但容易产生“这类状态该放哪”的模糊区。
- 调试时需要同时理解两套状态源，增加排查成本。
- 某些功能会逐渐穿透 UI 层和全局状态层，形成隐式耦合。

### 改进方向

- 为两套状态系统补充明确边界定义：
  - `bootstrap/state.ts` 只放非 React 生命周期依赖的运行时状态
  - `AppStateStore.ts` 只放 UI 交互和渲染所需共享状态
- 建立只读 selector/façade，减少模块直接读取底层状态。
- 对跨层状态同步建立固定入口，避免任意模块双向写入。

### 优先级

高

## 5. Feature flag 过多，增加静态理解成本

### 现状

- 代码大量使用 `feature('X')` 做构建时死代码消除。
- 许多模块通过条件 `require()` 加载不同能力。

### 问题

- 阅读代码时必须同时考虑“当前构建是否启用该能力”。
- 调试和重构时，容易遗漏某个变体路径。
- 条件导入分散在多个核心模块，导致主路径可读性下降。

### 改进方向

- 将 feature flag 的入口尽量收敛到少数装配模块。
- 为关键能力建立变体矩阵文档，明确哪些模块在什么构建下生效。
- 对高频 feature 组合建立集成测试或 smoke test。

### 优先级

中

## 6. 工具、命令、插件、技能、MCP 的扩展面很多，但统一抽象还不够强

### 现状

- 仓库同时存在 `commands/`、`tools/`、`plugins/`、`skills/`、`services/mcp/` 多套扩展机制。
- 不同扩展点各自有自己的注册、发现、加载和运行方式。

### 问题

- 新人很难快速判断“一个能力应该实现成 command、tool、skill 还是 plugin”。
- 运行期扩展能力强，但认知模型分散。
- 一些横切关注点，比如权限、可观测性、错误处理，可能在不同扩展面重复实现。

### 改进方向

- 输出一份“扩展点选择指南”，明确适用场景和边界。
- 抽象统一的 capability descriptor 或 registry 视图，用于展示和治理扩展能力。
- 统一扩展点的生命周期钩子、日志、权限、诊断模型。

### 优先级

中

## 7. 服务层目录体量很大，领域划分还可以再压实

### 现状

- `src/services/` 已经承担了大部分领域逻辑，方向是正确的。
- 但服务数量很多，领域间的层级深浅不完全一致。

### 问题

- `services/` 逐渐成为新的“大容器”。
- 同属一个业务域的代码，可能分散在 service、utils、hooks、tool 内。
- 领域边界不稳定时，后续更容易出现跨目录绕行依赖。

### 改进方向

- 对高复杂领域做 domain packing，例如把 memory、task、mcp、sandbox 各自内部再按子域收拢。
- 为每个核心域定义公开入口，减少横向直接穿透内部文件。
- 结合依赖分析，识别最常见的跨域反向依赖。

### 优先级

中

## 9. 超大文件仍是维护风险点

### 现状

- `root.ts`、`REPL.tsx`、`query.ts` 等核心文件都较重。
- 历史上已经做过多轮拆分，但主干文件仍然承担很多编排职责。

### 问题

- 代码评审困难。
- 冲突概率高。
- 局部优化常常需要先理解整条大链路。

### 改进方向

- 对超大文件做“先按阶段拆，再按领域拆”的两步拆分。
- 先把稳定接口提取出来，再移动实现，减少一次性大重构风险。
- 为重文件设置治理阈值，例如超出一定复杂度就禁止继续堆积。

### 优先级

高

## 10. 缺少一份面向维护者的“架构导航图”

### 现状

- 目录结构已经具备一定层次，但理解仍依赖阅读源码和历史上下文。

### 问题

- 新成员上手慢。
- 同一问题经常需要重复解释“应该改哪一层”。
- 架构边界容易在日常迭代中被侵蚀。

### 改进方向

- 增加维护者文档，至少覆盖：
  - 启动链路
  - 查询链路
  - 工具执行链路
  - 状态边界
  - 扩展点选择规则
- 用 1 到 2 张图说明主路径，而不是只靠目录说明。

### 优先级

高

## 建议的落地顺序

1. 先补文档，统一主链路和状态边界认知。
2. 拆 `root.ts` 的装配阶段，降低入口复杂度。
3. 拆 `REPL.tsx`，把 UI 容器与会话控制分离。
4. 继续拆 `query.ts`，把策略逻辑阶段化。
5. 最后再做扩展点治理和跨域依赖收敛。

## 适合继续展开的专题

- 启动链路重构方案
- REPL 容器拆分方案
- Query pipeline 分阶段方案
- 状态边界治理方案
- 扩展点统一治理方案
